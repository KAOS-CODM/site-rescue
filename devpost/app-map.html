Site Rescue — App Map

A compact take-home guide to how the app is put together. Snapshot of source commit a7aab55 — it can drift as work continues; re-check paths against the repo.

What it is

Paste a public website URL. Site Rescue crawls that site (the seed page plus up to 10 same-origin pages), runs 16 fixed checks per HTML page, and shows every finding with the evidence that proves it and which page it came from. Then an AI layer turns those findings into a rescue plan — Fix now / Fix next / Improve later — with an explanation and a developer task for each.

Two rules shape everything: the scanner is the source of truth (the AI never invents findings — every plan result must map to a real scanner finding, exactly once, or the plan is rejected), and the app is honest about what it couldn't check (partial scans say so; non-HTML responses only ever yield a factual HTTP-status finding).

The main pieces

  • public/ — the browser app: three-state UI (index.html + app.js), compiled Tailwind (styles.css), PWA shell (manifest.webmanifest, sw.js, icons/ — caches the shell only, never /api/*).
  • src/server.js — one Express process: serves the app, mounts POST /api/scan (SSE-style stream) and POST /api/plan.
  • src/scanner/ — SSRF-guarded fetch → cheerio parse → the 16 checks, inside a bounded same-origin crawl (crawl.js).
  • src/ai/ — provider adapter (OpenRouter) + validatePlan.js, the validator that keeps the AI honest.
  • src/checkConfig.js — every threshold in one place (page budget, byte cap, timeouts).

Reference route — 3 stops

A guided walk-through of one acceptance criterion: plan → code → evidence. If you toured these live in the Code Tour, they are your tour stops; otherwise use them as a reference route.

Stop 1 · the plan

devpost/spec.md — search “Plan validator”

The acceptance criterion written before any adapter code existed: every plan findingId must exist in the scanner’s input and every input finding must appear exactly once — invented, missing, or duplicated IDs reject the whole plan. Observable and mechanical, so “does the agent’s output pass?” never required trusting the agent.

Stop 2 · the code

src/ai/validatePlan.js — search validatePlan(plan, findings)

inputIds/inputSet are built from the scanner’s findings; a seen map counts duplicates; a final loop checks every input id appears. Any miss returns { ok: false, reason }, which src/server.js (search ai_failed) turns into a 502 { error: 'ai_failed' } — the UI then keeps the findings and shows the honest failure panel with Retry rescue plan (search ai-failure in public/index.html).

Stop 3 · the observed result

devpost/checklist.md — slice 3, Verify (mechanical)

The recorded evidence: fixture outputs containing an invented ID, a missing ID, and a duplicate ID → all three rejected; plus the Final Review verification record — live OpenRouter plans where every result mapped to a real scanner finding exactly once (full suite 463/463). The criterion → the check → the observation, in one line.

A practice to reuse — grounded in this project

The decision: before the AI adapter was written, the spec stated how we would know it worked — “every result maps to exactly one real scanner finding; invented, missing, or duplicate IDs → reject.”

The evidence: devpost/spec.md § Plan validator → src/ai/validatePlan.js → devpost/checklist.md slice 3 Verify (mechanical) (three fixture attacks, all rejected) and the Final Review record (live plans, ID-exact, 463/463 suite).

Reuse it: on any agent-assisted project, write “how we’ll prove this works” as an observable, mechanical rule before the build starts. The agent then builds toward a checkable target, and verification — not trust — answers whether it’s done.

Run it again: npm install → copy .env.example to .env and add your OpenRouter key → npm start → open http://localhost:3000 (full steps in README.md).
